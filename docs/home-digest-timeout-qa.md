# 今日 AI 日报超时：真实复现与修复

验证日期：2026-10-18。用户截图中的失败来自「今日 AI 日报」，不是尚未启用的「今日值得看」。

## 调查与实际证据

- 当前日报使用 `grok-4.7`，连接为 auto 且已识别 Responses；档案的 `reasoning_effort` 为空，首页调用未指定默认值，因而继承服务端行为。
- 原路径重放缓存中的公开资讯：提示词约 5108 字符，三个有内容分节，共 21 个候选条目，60.29 秒触发外层 `TimeoutError`；原模型时限为 60 秒。
- 同模型、协议和连接的极小 JSON 探针：非流式 8.33 秒、流式 7.69 秒成功，排除了完全无法连通以及单纯“非流式不可用”的假设。
- 只把推理强度设为 `low`，保留原模型、公开资讯、输出上限和超时：完整日报 21.34 秒成功，JSON 可解析，包含三个分节。
- 修复后通过实际 `digest.regenerate()` 工作线程重新生成：24.27 秒完成。随后重新读取原账号工作区缓存和模型监控：状态 `ready`、日期 `2026-10-18`、有总览和三个分节、错误为空；真实模型事件为 Responses 成功，耗时 23963 ms。
- 再次读取已保存模型档案，`reasoning_effort` 仍为空，确认没有修改用户档案或全局聊天设置。此处记录的是一次故障及对照观察，不代表服务商时延保证。

调查未记录 API Key、认证头、私人对话或文件；报告不复制实际资讯正文或用户标识。

## 代码修复

`backend/app/feeds/digest.py` 的单次首页文本适配在档案未明确指定时，使用调用级 `reasoning_effort=low`；显式 `low` / `medium` / `high` 继续优先。资讯精选复用同一适配，也得到这个默认值。没有修改全局聊天、模型档案、输出上限或 60 秒配置，没有自动换模型或增加失败重试。

外层 `asyncio.timeout` 通过取消退出 provider，而 `CancelledError` 不属于普通 `Exception`，因此旧路径在界面报超时的同时可能没有模型失败记录。现在在外层截止处按现有调用身份补记 `request_timeout` 并重新抛出原超时；普通 provider 错误不额外重复记录，监控写入失败不覆盖原错误。
